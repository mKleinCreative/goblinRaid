## #331 — ROOT CAUSE FOUND. The ticket's hypothesis is WRONG, and so was my first answer.

**Strike the ticket's "reorder BT node [6]" plan. Do not rewrite `BT_Defender`'s patrol branch.**

I first claimed the branch was hand-rolled and should use `ACFPatrolSplinePathTask`. **That was
wrong.** I walked ACF's own trees: `ACFBT` has the *identical* branch (`MoveTo` ->
`WaitBlackboardTime` -> `Sequence` -> `GoToNextWayPoint_C`) and `ACF_HorseBT` shares the shape.
`BT_Defender` is a faithful copy. Changing it would be diverging from ACF — the exact mistake this
project keeps paying for.

**The real gap.** `UACFAIPatrolComponent::StartPatrolLoop()` is the only thing that seeds a patrol
and binds `HandleMoveCompleted` (which re-requests a waypoint after each completed move). ACF ships
callers **only** in its ROUTINE tasks — `ACFPatrolSplinePathTask`, `ACFFollowSplinePathTask`,
`ACFRandomPatrolAroundPointTask` — each of which sets the path, sets the AI state and starts the loop
together. `ACFPatrolSplinePathTask` is **not a BT node**; it is an ACF routine task
(`OnTaskStarted_Implementation(const APawn*)`).

Our guards are **placed in the level** with `PathToFollow` authored on the component, so they never
run a routine and nothing ever made the call. The component's header states the contract plainly:

> *"Call StartPatrolLoop() once the owning pawn has a valid AACFAIController."*

**Measured in PIE on `L_Tutorial_Island`:** all 7 placed guards reported `IsPatrolLoopActive()`
false; one `StartPatrolLoop(true)` each and **5 of 7 were walking their `GS_Road` splines** on the
next sample.

**Fix, written but NOT COMPILED (#339):** `AGSAIControllerBase::OnPossess` calls
`StartPatrolLoop(true)` when the pawn has a patrol component with a route. Guarded so a spline
patroller with no path is skipped and horde goblins (no such component) are untouched.

Two loose ends in the level data, neither explained:

- All five `GS_Guard_A1..B2` share the **same** spline `ACF_SplinePath_BP_C_13`. Probably not intended.
- `BP_CastleGuard02_C_1` returned `True` from a manual `TryGoToNextWaypoint` in an earlier session

## TRAPS LEARNED TODAY — these are the expensive ones

1. **A dead probe returns the REF POSE, and for this rig the ref pose IS a T-pose.** I built a
   `SkeletalMeshActor` in single-node mode to sample bones. It silently stops ticking when its anim
   asset is overwritten underneath it; `get_position()` then returns 0.000 and `get_bone_transform`
   hands back the ref pose. **I read three poses off a corpse and stated a wrong conclusion to
   Michael.** Print `get_position()` beside every probe reading and treat an unchanged value as a
   dead instrument. Better: **compose the bone chain from asset data** —
   `AnimationLibrary.get_bone_pose_for_frame` + `MathLibrary.compose_transforms`, root to leaf. Needs
   no ticking, works during PIE, and is what every trustworthy number here rests on.
2. **`set_position()` does not evaluate the pose in the editor.** My first probe returned identical
   numbers for four different clips including Idle. Always run a CONTROL — sample something you know
   differs, and if the numbers match, your instrument is dead.
3. **A retargeter setting proves nothing until every clip is re-run through it.** I ran
   `auto_align_all_bones` after batching 19 clips, then re-retargeted only one to test it. The other
   18 kept the unaligned pose, and Michael opened one and saw a T-pose.
4. **`AnimMontage.SequenceLength` is read-only from Python and nothing reachable recalculates it**
   (reload, rate_scale nudge, notify add/remove all fail — three attempts, then stop). It does not
   matter: `UAnimMontage::PostLoad` (`Engine/Private/Animation/AnimMontage.cpp:464-470`) detects the
   mismatch, logs *"Please resave the asset"* and fixes it on load. Resave to clear the log line.
5. **ACF BUG — `SetLocomotionStateSpeed` can crash.** It dereferences
   `LocomotionStates.FindByKey(State)->StateModifier` unguarded
   (`ACFCharacterMovementComponent.cpp:294`). On a character whose bands were emptied that is a null
   deref. Set the `LocomotionStates` array directly — it is `BlueprintReadWrite`.
6. **`SetLocomotionState` early-returns when the target state already matches**, so testing with the
   default (`EWalk`) looks like a no-op and reads as failure.
7. **`FACFLocomotionState.State` is `EditDefaultsOnly`** and refuses `set_editor_property`;
   `import_text()` on the struct bypasses it. (Same as handoff A's gotcha 6.)
8. **Unreal's Python bindings strip the leading `b` from bool UPROPERTYs** — `bDisarmLocomotionStates`
   is `disarm_locomotion_states`.
9. **`gsqueue.ps1 set -Agent` silently does nothing.** It reports success but the board still prints
   `unassigned`, which is why #331 kept tripping the STALE warning all session after Michael had
   assigned it to me. `-Agent` appears to apply only at `claim` time. Worth fixing.
10. **Confirmed again, twice:** during PIE `get_editor_world()` returns None and
    `get_all_level_actors()` is empty — that means PIE is running, not that actors were deleted. Use
    `UnrealEditorSubsystem.get_game_world()` in PIE.
11. **The editor can come back on the wrong map.** After a restart it opened `L_CombatArena`, not
    `L_Tutorial_Island` — 71 actors, no roads, 4 guards. Check `get_game_world().get_name()` before
    concluding anything about a level.
12. **The editor can also come back on the wrong PROJECT.** A process that "won't open" may be
    loading `D:\UE_5.8\Unreal Projects\FullExample`. Check the command line with
    `Get-CimInstance Win32_Process | Select CommandLine` before diagnosing a crash — there was none.
